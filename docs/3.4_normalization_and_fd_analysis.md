## 1. Introduction & Formal Definitions

Normalization is a systematic, mathematically grounded technique used in relational database design to:
1. **Eliminate data redundancy:** Prevent duplicate storage of real-world facts.
2. **Prevent update, insertion, and deletion anomalies:** Ensure mutations maintain data integrity.
3. **Preserve data dependencies and lossless joins:** Guarantee that decomposed relations can reconstruct the original database without spurious tuples.

### Formal Notation & Definitions

* **Relation Schema:** $R(A_1, A_2, \dots, A_n)$ where each $A_i$ is an attribute over domain $dom(A_i)$.
* **Functional Dependency (FD):** Given relation $R$, a functional dependency $X \to Y$ (where $X, Y \subseteq R$) asserts that for any two valid tuples $t_1, t_2 \in R$, if $t_1[X] = t_2[X]$, then $t_1[Y] = t_2[Y]$. $X$ is called the **determinant**, and $Y$ is the **dependent**.
* **Trivial Dependency:** $X \to Y$ is trivial if $Y \subseteq X$.
* **Full Functional Dependency:** In $R$, $X \to Y$ is a full functional dependency if removal of any attribute $A \in X$ invalidates the dependency (i.e., $\forall A \in X, (X \setminus \{A\}) \not\to Y$).
* **Partial Functional Dependency:** $X \to Y$ is partial if there exists some proper subset $X' \subset X$ such that $X' \to Y$.
* **Transitive Dependency:** Given $X \to Y$ and $Y \to Z$ where $Y \not\to X$ and $Z \not\subseteq Y$, then $X \to Z$ is a transitive dependency.
* **Superkey:** A subset of attributes $K \subseteq R$ such that $K \to R$.
* **Candidate Key:** A minimal superkey (no proper subset of $K$ is a superkey).
* **Prime Attribute:** Any attribute that is a member of at least one candidate key of $R$. Non-prime attributes do not belong to any candidate key.

## 3. Candidate Key Selection & Attribute Closure ($X^+$)

To formally prove that the chosen primary keys are valid candidate keys, we compute the **Attribute Closure** ($X^+$) under the set of functional dependencies $F$ using Armstrong's Axioms.

### 3.1 Axiomatic Foundations (Armstrong's Inference Rules)

1. **Reflexivity:** If $Y \subseteq X$, then $X \to Y$.
2. **Augmentation:** If $X \to Y$, then $XZ \to YZ$.
3. **Transitivity:** If $X \to Y$ and $Y \to Z$, then $X \to Z$.
4. **Union (Derived):** If $X \to Y$ and $X \to Z$, then $X \to YZ$.
5. **Decomposition (Derived):** If $X \to YZ$, then $X \to Y$ and $X \to Z$.
6. **Pseudotransitivity (Derived):** If $X \to Y$ and $WY \to Z$, then $WX \to Z$.

### Closure Algorithm
$$\text{Input: Set of attributes } X, \text{ set of FDs } F$$
$$\text{Output: Attribute closure } X^+$$
1. $X^{(0)} = X$
2. $X^{(i+1)} = X^{(i)} \cup \{A \mid \exists (Y \to Z) \in F \text{ such that } Y \subseteq X^{(i)} \text{ and } A \in Z\}$
3. Repeat step 2 until $X^{(i+1)} = X^{(i)}$. Return $X^+$.

### 3.2 Detailed Closure Computations for Key Relations

#### Case 1: Relation $R_6$ (`shelter_inventory`)
* **Relation Schema:**
  $$R_6 = \{\text{shelter\_id}, \text{resource\_id}, \text{quantity}, \text{reorder\_level}, \text{last\_updated}\}$$
* **Given FDs ($F_6$):**
  $$f_1: \{\text{shelter\_id}, \text{resource\_id}\} \to \{\text{quantity}, \text{reorder\_level}, \text{last\_updated}\}$$

**Test Candidate Key:** $K = \{\text{shelter\_id}, \text{resource\_id}\}$

* **Iteration 0:**
  $$X^{(0)} = \{\text{shelter\_id}, \text{resource\_id}\}$$
* **Iteration 1:**
  Applying $f_1$ (since $\{\text{shelter\_id}, \text{resource\_id}\} \subseteq X^{(0)}$):
  $$X^{(1)} = X^{(0)} \cup \{\text{quantity}, \text{reorder\_level}, \text{last\_updated}\}$$
  $$X^{(1)} = \{\text{shelter\_id}, \text{resource\_id}, \text{quantity}, \text{reorder\_level}, \text{last\_updated}\} = R_6$$
* **Termination:** $X^{(1)} = R_6$. Therefore, $\{\text{shelter\_id}, \text{resource\_id}\}$ is a **superkey**.

**Minimality Proof (Checking Proper Subsets):**
1. Subset $S_1 = \{\text{shelter\_id}\}$:
   * $S_1^{(0)} = \{\text{shelter\_id}\}$
   * No FD in $F_6$ has LHS $\subseteq S_1^{(0)}$.
   * $S_1^+ = \{\text{shelter\_id}\} \neq R_6$.
2. Subset $S_2 = \{\text{resource\_id}\}$:
   * $S_2^{(0)} = \{\text{resource\_id}\}$
   * No FD in $F_6$ has LHS $\subseteq S_2^{(0)}$.
   * $S_2^+ = \{\text{resource\_id}\} \neq R_6$.

$$\therefore \{\text{shelter\_id}, \text{resource\_id}\} \text{ is a minimal superkey } \implies \textbf{Valid Candidate Key.}$$

---

#### Case 2: Relation $R_2$ (`zones`)
* **Relation Schema:**
  $$R_2 = \{\text{zone\_id}, \text{disaster\_id}, \text{name}, \text{severity}, \text{primary\_shelter\_id}, \text{coordinator\_contact}\}$$
* **Given FDs ($F_2$):**
  $$f_1: \{\text{zone\_id}\} \to \{\text{disaster\_id}, \text{name}, \text{severity}, \text{primary\_shelter\_id}, \text{coordinator\_contact}\}$$
  $$f_2: \{\text{disaster\_id}, \text{name}\} \to \{\text{zone\_id}, \text{severity}, \text{primary\_shelter\_id}, \text{coordinator\_contact}\}$$

**Candidate Key 1:** $K_1 = \{\text{zone\_id}\}$
* $X^{(0)} = \{\text{zone\_id}\}$
* Applying $f_1$: $X^{(1)} = \{\text{zone\_id}, \text{disaster\_id}, \text{name}, \text{severity}, \text{primary\_shelter\_id}, \text{coordinator\_contact}\} = R_2$
* Since $K_1$ is a singleton set, it has no non-empty proper subsets.
* $\therefore \{\text{zone\_id}\}$ is a **Candidate Key (Selected as Primary Key)**.

**Candidate Key 2 (Alternate Key):** $K_2 = \{\text{disaster\_id}, \text{name}\}$
* $X^{(0)} = \{\text{disaster\_id}, \text{name}\}$
* Applying $f_2$: $X^{(1)} = \{\text{disaster\_id}, \text{name}, \text{zone\_id}, \text{severity}, \text{primary\_shelter\_id}, \text{coordinator\_contact}\} = R_2$
* Proper subsets:
  * $\{\text{disaster\_id}\}^+ = \{\text{disaster\_id}\} \neq R_2$
  * $\{\text{name}\}^+ = \{\text{name}\} \neq R_2$
* $\therefore \{\text{disaster\_id}, \text{name}\}$ is an **Alternate Candidate Key**.

---

#### Case 3: Relation $R_{10}$ (`resource_requests`)
* **Relation Schema:**
  $$R_{10} = \{\text{request\_id}, \text{zone\_id}, \text{resource\_id}, \text{quantity\_requested}, \text{urgency}, \text{priority\_score}, \text{status}, \text{requested\_at}, \text{fulfilled\_at}\}$$
* **Given FDs ($F_{10}$):**
  $$f_1: \{\text{request\_id}\} \to \{\text{zone\_id}, \text{resource\_id}, \text{quantity\_requested}, \text{urgency}, \text{priority\_score}, \text{status}, \text{requested\_at}, \text{fulfilled\_at}\}$$
  $$f_2: \{\text{urgency}, \text{quantity\_requested}\} \to \{\text{priority\_score}\}$$

**Test Candidate Key:** $K = \{\text{request\_id}\}$
* $X^{(0)} = \{\text{request\_id}\}$
* Applying $f_1$: $X^{(1)} = R_{10}$
* Since $K$ is a singleton, no proper subset can be tested.
* $\therefore \{\text{request\_id}\}$ is a **Candidate Key (Primary Key)**.

## 4. Demonstration of the Normalization Process (UNF to BCNF)

To demonstrate the full normalization trajectory, consider a naive, unnormalized spreadsheet often used by field coordinators during initial disaster relief operations:

### Universal Relation: `Universal_Disaster_Logistics` (UNF)

$$\text{UNF}(\text{DisasterName}, \text{DisasterType}, \text{DisasterSeverity}, \text{ZoneName}, \text{ZoneSeverity}, \text{ShelterName}, \text{ShelterLocation}, \text{ShelterCapacity}, \text{ResourceName}, \text{CategoryName}, \text{QuantityInStock}, \text{ReorderLevel}, \text{VolunteerName}, \text{VolunteerSkills}, \text{ShiftDutyPeriod})$$

### Anomalies in the Universal Relation
1. **Insertion Anomaly:** Cannot register a newly opened shelter or incoming resource catalog item until an affected zone or volunteer is assigned.
2. **Deletion Anomaly:** If the only volunteer working in a zone is deleted, the entire shelter inventory record and zone severity data are accidentally lost.
3. **Update Anomaly:** If a shelter's capacity changes, multiple redundant rows must be updated; any missed row creates inconsistent capacity data.

---

### Step 1: Transformation from UNF to 1NF (First Normal Form)

> **Definition (1NF):** A relation $R$ is in 1NF if and only if all underlying domains contain only **atomic (indivisible) values**, and there are no repeating groups or multivalued attributes.

#### Violations in UNF:
1. **Composite Attribute:** `ShelterLocation` contains paired coordinates (e.g., `"11.5564° N, 76.1384° E"`).
2. **Multivalued Attribute:** `VolunteerSkills` contains non-atomic comma-separated lists (e.g., `"First Aid, Heavy Driving, Boat Rescue"`).
3. **Repeating Groups:** A single shelter contains multiple resource items and multiple volunteer shifts.

#### 1NF Decomposition Actions:
1. Decompose `ShelterLocation` into atomic sub-attributes: `location_latitude` (DOUBLE PRECISION) and `location_longitude` (DOUBLE PRECISION).
2. Represent multivalued `VolunteerSkills` using PostgreSQL's atomic array type `TEXT[]` or decompose into a normalized relation:
   $$\text{VOLUNTEER\_SKILLS}(\underline{\text{volunteer\_id}}, \underline{\text{skill\_name}})$$
3. Eliminate repeating groups by splitting into distinct flat records.

---

### Step 2: Transformation from 1NF to 2NF (Second Normal Form)

> **Definition (2NF):** A relation $R$ is in 2NF if and only if:
> 1. It is in 1NF.
> 2. **No non-prime attribute is partially dependent on any candidate key** (i.e., every non-prime attribute is fully functionally dependent on every candidate key).

#### Identified Partial Dependency Violation:
Consider the intermediate 1NF relation for relief inventory:
$$R_{\text{inv\_1NF}}(\underline{\text{shelter\_id}}, \underline{\text{resource\_id}}, \text{shelter\_name}, \text{capacity}, \text{resource\_name}, \text{unit}, \text{quantity}, \text{reorder\_level})$$

* **Candidate Key:** $\{\text{shelter\_id}, \text{resource\_id}\}$
* **Prime Attributes:** `shelter_id`, `resource_id`
* **Non-Prime Attributes:** `shelter_name`, `capacity`, `resource_name`, `unit`, `quantity`, `reorder_level`

**Functional Dependencies Present:**
* $f_1: \{\text{shelter\_id}, \text{resource\_id}\} \to \{\text{quantity}, \text{reorder\_level}\}$ (**Full Dependency**)
* $f_2: \{\text{shelter\_id}\} \to \{\text{shelter\_name}, \text{capacity}\}$ (**Partial Dependency!** Dependent on subset of composite PK)
* $f_3: \{\text{resource\_id}\} \to \{\text{resource\_name}, \text{unit}\}$ (**Partial Dependency!** Dependent on subset of composite PK)

#### 2NF Decomposition:
To achieve 2NF, we remove the partially dependent attributes into their own relations whose primary keys match the determinant of the partial dependency:

1. **`SHELTERS`** (eliminates $f_2$):
   $$\text{SHELTERS}(\underline{\text{shelter\_id}}, \text{shelter\_name}, \text{capacity})$$
2. **`RESOURCES`** (eliminates $f_3$):
   $$\text{RESOURCES}(\underline{\text{resource\_id}}, \text{resource\_name}, \text{unit})$$
3. **`SHELTER_INVENTORY`** (retains only full dependency $f_1$):
   $$\text{SHELTER\_INVENTORY}(\underline{\text{shelter\_id}}^*, \underline{\text{resource\_id}}^*, \text{quantity}, \text{reorder\_level})$$

$$\implies \text{All three decomposed relations satisfy 2NF.}$$

---

### Step 3: Transformation from 2NF to 3NF (Third Normal Form)

> **Definition (3NF):** A relation $R$ is in 3NF if and only if:
> 1. It is in 2NF.
> 2. **No non-prime attribute is transitively dependent on any candidate key.**  
> *(Equivalently: for every non-trivial FD $X \to Y$, either $X$ is a superkey OR $Y$ is a prime attribute).*

#### Identified Transitive Dependency Violation 1: Zones & Disasters
Consider an un-decomposed 2NF relation for zones:
$$R_{\text{zone\_2NF}}(\underline{\text{zone\_id}}, \text{zone\_name}, \text{zone\_severity}, \text{disaster\_id}, \text{disaster\_name}, \text{disaster\_severity}, \text{disaster\_status})$$

* **Candidate Key:** $\{\text{zone\_id}\}$
* **Functional Dependencies:**
  * $f_1: \{\text{zone\_id}\} \to \{\text{zone\_name}, \text{zone\_severity}, \text{disaster\_id}\}$
  * $f_2: \{\text{disaster\_id}\} \to \{\text{disaster\_name}, \text{disaster\_severity}, \text{disaster\_status}\}$
* **Transitive Dependency:**
  $$\{\text{zone\_id}\} \xrightarrow{f_1} \{\text{disaster\_id}\} \xrightarrow{f_2} \{\text{disaster\_name}, \text{disaster\_severity}, \text{disaster\_status}\}$$
  Here, non-prime attributes `disaster_name`, `disaster_severity`, and `disaster_status` depend on `disaster_id`, which is **not** a superkey in $R_{\text{zone\_2NF}}$.

#### 3NF Decomposition 1:
Decompose $R_{\text{zone\_2NF}}$ into:
1. **`DISASTERS`**:
   $$\text{DISASTERS}(\underline{\text{disaster\_id}}, \text{name}, \text{severity}, \text{status})$$
2. **`ZONES`**:
   $$\text{ZONES}(\underline{\text{zone\_id}}, \text{disaster\_id}^*, \text{name}, \text{severity})$$

---

#### Identified Transitive Dependency Violation 2: Resources & Categories
Consider an un-decomposed 2NF relation for catalog items:
$$R_{\text{res\_2NF}}(\underline{\text{resource\_id}}, \text{name}, \text{unit}, \text{category\_id}, \text{category\_name})$$

* **Candidate Key:** $\{\text{resource\_id}\}$
* **Functional Dependencies:**
  * $f_1: \{\text{resource\_id}\} \to \{\text{name}, \text{unit}, \text{category\_id}\}$
  * $f_2: \{\text{category\_id}\} \to \{\text{category\_name}\}$
* **Transitive Dependency:**
  $$\{\text{resource\_id}\} \to \{\text{category\_id}\} \to \{\text{category\_name}\}$$

#### 3NF Decomposition 2:
Decompose $R_{\text{res\_2NF}}$ into:
1. **`RESOURCE_CATEGORIES`**:
   $$\text{RESOURCE\_CATEGORIES}(\underline{\text{category\_id}}, \text{name})$$
2. **`RESOURCES`**:
   $$\text{RESOURCES}(\underline{\text{resource\_id}}, \text{name}, \text{category\_id}^*, \text{unit})$$

$$\implies \text{All decomposed relations satisfy 3NF.}$$

---

### Step 4: Verification of Boyce-Codd Normal Form (BCNF)

> **Definition (BCNF):** A relation $R$ is in BCNF if and only if for **every non-trivial functional dependency $X \to Y$, $X$ is a superkey of $R$**.  
> *(BCNF is strictly stronger than 3NF because it removes the "or $Y$ is a prime attribute" exception).*

Let us verify BCNF compliance across all 14 relations in the DRRAS schema:

|:---|:---|:---|:---:|:---:|

| **`zones`** | $\{\text{zone\_id}\} \to \text{all other attrs}$<br>$\{\text{disaster\_id}, \text{name}\} \to \text{all other attrs}$ | `zone_id`<br>`{disaster_id, name}` | **Yes** (PK)<br>**Yes** (Candidate Key) | **Yes** |

| **`resources`** | $\{\text{resource\_id}\} \to \text{all other attrs}$ | `resource_id` | **Yes** (Primary Key) | **Yes** |
| **`shelter_inventory`** | $\{\text{shelter\_id}, \text{resource\_id}\} \to \text{all other attrs}$ | `{shelter_id, resource_id}` | **Yes** (Composite PK) | **Yes** |
| **`people`** | $\{\text{person\_id}\} \to \text{all other attrs}$ | `person_id` | **Yes** (Primary Key) | **Yes** |

| **`resource_requests`** | $\{\text{request\_id}\} \to \text{all other attrs}$<br>$\{\text{urgency}, \text{qty}\} \to \text{priority\_score}$ | `request_id`<br>`{urgency, qty}` | **Yes** (PK)<br>*Generated Expression* | **Yes** |

$$\therefore \textbf{Every relation in the DRRAS relational schema is in Boyce-Codd Normal Form (BCNF).}$$

## 5. Mathematical Proof of Decomposition Properties

Any relational decomposition $D = \{R_1, R_2, \dots, R_k\}$ must satisfy two essential mathematical criteria:
1. **Lossless-Join Property (Guaranteed Reconstruction)**
2. **Dependency Preservation Property (Efficient Constraint Verification)**

### 5.1 Lossless-Join Decomposition Proof

> **Theorem (Binary Lossless Join):** A decomposition of relation $R$ into $R_1$ and $R_2$ is lossless with respect to a set of functional dependencies $F$ if and only if the common attribute(s) form a superkey of at least one of the decomposed relations:
> $$(R_1 \cap R_2) \to R_1 \quad\text{OR}\quad (R_1 \cap R_2) \to R_2$$

#### Proof Example: Decomposition of Inventory into `SHELTERS` and `SHELTER_INVENTORY`
* Original relation: $R = \{\text{shelter\_id}, \text{name}, \text{capacity}, \text{resource\_id}, \text{quantity}\}$
* Decomposed into:
  * $R_1 = \text{SHELTERS}(\underline{\text{shelter\_id}}, \text{name}, \text{capacity})$
  * $R_2 = \text{SHELTER\_INVENTORY}(\underline{\text{shelter\_id}}^*, \underline{\text{resource\_id}}^*, \text{quantity})$

1. **Common Attributes:**
   $$R_1 \cap R_2 = \{\text{shelter\_id}\}$$
2. **Evaluating $(R_1 \cap R_2)^+$ under $F$:**
   $$\{\text{shelter\_id}\}^+ = \{\text{shelter\_id}, \text{name}, \text{capacity}\} = R_1$$
3. Since $(R_1 \cap R_2) \to R_1$, the common attribute set forms a superkey for $R_1$.

$$\therefore \text{The natural join } R_1 \bowtie R_2 \equiv R \implies \textbf{Lossless Join Guaranteed.}$$

---

### 5.2 Dependency Preservation Proof

> **Theorem (Dependency Preservation):** A decomposition $D = \{R_1, R_2, \dots, R_k\}$ preserves a set of functional dependencies $F$ if:
> $$F' = (F_1 \cup F_2 \cup \dots \cup F_k) \equiv F$$
> where $F_i$ is the projection of $F$ onto $R_i$:
> $$F_i = \pi_{R_i}(F) = \{X \to Y \in F^+ \mid X \cup Y \subseteq R_i\}$$

#### Verification across Decompositions:
* All functional dependencies involving disaster data reside within $R_1$ (`disasters`).
* All dependencies involving zone allocations reside within $R_2$ (`zones`).
* All stock balance dependencies reside within $R_6$ (`shelter_inventory`).
* Foreign key constraints enforced by the database guarantee that inter-relational referential integrity is checked without computing multi-table joins.

$$\therefore \textbf{All functional dependencies are preserved across the decomposed schema.}$$

## 6. Higher Normal Forms: Fourth Normal Form (4NF) Analysis

> **Definition (4NF):** A relation $R$ is in 4NF if and only if for every non-trivial **Multivalued Dependency (MVD)** $X \twoheadrightarrow Y$, $X$ is a superkey of $R$.

### Context in DRRAS: Volunteer Profiles & Multi-Valued Attributes

Suppose a naive designer attempted to combine a volunteer's multiple skills and multiple assigned zones into a single relation:
$$R_{\text{bad}}(\underline{\text{volunteer\_id}}, \underline{\text{skill}}, \underline{\text{zone\_id}})$$

* **Observation:** Skills and zones are mutually independent real-world concepts. A volunteer having skill "First Aid" has nothing to do with whether they are deployed to Zone 1 or Zone 2.
* **Multivalued Dependencies:**
  $$\text{volunteer\_id} \twoheadrightarrow \text{skill}$$
  $$\text{volunteer\_id} \twoheadrightarrow \text{zone\_id}$$
* In $R_{\text{bad}}$, the candidate key is the entire triplet $\{\text{volunteer\_id}, \text{skill}, \text{zone\_id}\}$.
* The determinant `volunteer_id` is **not** a superkey. This introduces Cartesian product redundancy (if a volunteer has 3 skills and 4 zone shifts, $3 \times 4 = 12$ rows are stored).

### DRRAS Solution to Ensure 4NF:
In DRRAS, this MVD is cleanly resolved using two complementary architectural choices:
1. **Relational Separation:** Volunteer zone deployments are isolated in `volunteer_shifts` ($R_{12}$), where each row binds a volunteer to a single zone for a specific duty period:
   $$\text{VOLUNTEER\_SHIFTS}(\underline{\text{shift\_id}}, \text{volunteer\_id}^*, \text{zone\_id}^*, \text{duty\_period})$$
2. **Native PostgreSQL Array Type:** Skills are encapsulated as an atomic PostgreSQL vector (`TEXT[]`) within $R_8$ (`volunteers`):
   $$\text{VOLUNTEERS}(\underline{\text{person\_id}}^*, \text{skills}, \text{availability}, \text{assigned\_zone}^*)$$

By ensuring that independent multi-valued facts never share a composite key in the same relation:

$$\therefore \textbf{The DRRAS schema satisfies Fourth Normal Form (4NF).}$$
