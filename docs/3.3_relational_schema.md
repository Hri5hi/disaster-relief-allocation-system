## Notation Guide

The following conventions are used throughout this section:

| Notation | Meaning |
|---|---|
| **<u>attribute</u>** | Primary Key attribute (underlined) |
| attribute* | Foreign Key attribute (asterisk suffix) |
| [attribute] | Optional / nullable attribute |
| {attribute} | Multivalued attribute (stored as PostgreSQL array or JSONB) |
| attribute° | Derived / Generated attribute (computed by the database) |

---

## ER-to-Relational Mapping Rules Applied

Before presenting the schema, the following standard mapping rules are applied to translate the ER design into relations:

| ER Construct | Mapping Rule Applied |
|---|---|
| **Strong entity** | Becomes a relation; primary key = entity key attribute |
| **Binary 1:N relationship** | FK placed on the "many" side, referencing the "one" side's PK |
| **Binary M:N relationship** | New junction/bridge relation created with composite PK of both entity PKs |
| **ISA / Specialization** | Both superclass and subclass become separate relations; subclass inherits and includes superclass PK as its own PK (Table-per-Type mapping) |
| **Composite attribute** | Stored as a structured PostgreSQL composite type or decomposed into atomic sub-attributes |
| **Multivalued attribute** | Stored using PostgreSQL's native `TEXT[]` array or `JSONB` type in-line |
| **Derived attribute** | Stored as a PostgreSQL **generated column** auto-computed by the database engine |
| **Self-referencing relationship** | FK in the same relation that references its own PK (used for hierarchical categories) |

## Group 1: Disaster & Zone Management

### Relation 1 — `disasters`

**Relational Schema:**

> disasters(**disaster_id**, name, type, severity, active_period, status, created_at)

**Attribute Descriptions:**

| Attribute | Type | Constraints | Description |
|---|---|---|---|
| `disaster_id` | INTEGER | **PRIMARY KEY**, AUTO INCREMENT | Surrogate key that uniquely identifies each disaster event. Auto-incremented by the database so no application-level ID generation is needed. |
| `name` | VARCHAR(100) | NOT NULL | Human-readable name of the disaster event, e.g., *"Kerala Floods 2026"* or *"Wayanad Landslide 2026"*. Must not be null since a disaster record without a name is meaningless. |
| `type` | VARCHAR(50) | OPTIONAL | Categorical classification of the disaster type: `'flood'`, `'earthquake'`, `'cyclone'`, `'landslide'`, etc. Used for filtering and reporting across disaster types. |
| `severity` | VARCHAR(10) | CHECK(`'low'`, `'medium'`, `'high'`, `'critical'`) | Overall severity level of the disaster as assessed by administrators. A CHECK constraint enforces a controlled vocabulary, preventing invalid values. Drives resource allocation priority globally. |
| `active_period` | DATERANGE | OPTIONAL | A PostgreSQL native **range type** storing the start and end dates of the disaster's active phase as a single attribute, e.g., `'[2026-07-01, 2026-07-15)'`. Supports operators like `@> CURRENT_DATE` (is today inside the period?) enabling powerful temporal queries without manual date comparison logic. |
| `status` | VARCHAR(20) | CHECK(`'active'`, `'monitoring'`, `'resolved'`, `'closed'`) | Lifecycle state of the disaster. When status is set to `'resolved'`, a database trigger (`trg_cascade_disaster_close`) automatically cancels all pending resource requests for that disaster — zero application code needed. |
| `created_at` | TIMESTAMPTZ | DEFAULT NOW() | Timestamp of when the disaster record was created. Auto-populated by the database. |

**Relationships Involving `disasters`:**
- `disasters` is the **root entity** of the entire system. Every zone, resource request, volunteer shift, and affected person traces back to a disaster event.
- **1:N with `zones`** — One disaster can affect many geographic zones; each zone belongs to exactly one disaster. Implemented by placing `disaster_id` as a FK in `zones`.

### Relation 2 — `zones`

**Relational Schema:**

> zones(**zone_id**, disaster_id\*, name, severity, [primary_shelter_id\*], [coordinator_contact])

**Attribute Descriptions:**

| Attribute | Type | Constraints | Description |
|---|---|---|---|
| `zone_id` | INTEGER | **PRIMARY KEY**, AUTO INCREMENT | Surrogate key uniquely identifying a geographic zone affected by a disaster. |
| `disaster_id` | INTEGER | NOT NULL, **FK → disasters(disaster_id)** | Foreign key linking this zone to the disaster it belongs to. NOT NULL because a zone without a disaster association has no operational context. |
| `name` | VARCHAR(100) | NOT NULL | Descriptive name of the affected zone, e.g., *"Wayanad North Sector"*, *"Meppadi Relief Zone"*. Meaningful to field coordinators who operate within these zones. |
| `severity` | VARCHAR(10) | CHECK(`'low'`, `'medium'`, `'high'`, `'critical'`) | Zone-level severity, which may differ from the parent disaster's severity. A northern sector of a flood zone may be `'critical'` while a southern sector is only `'medium'`. Used to prioritize resource allocation across zones of the same disaster. |
| `primary_shelter_id` | INTEGER | NULLABLE, **FK → shelters(shelter_id)** | References the main relief shelter designated to serve this zone. Optional because zones may be defined before shelters are registered. |
| `coordinator_contact` | VARCHAR(20) | OPTIONAL | Phone number of the Zone Coordinator responsible for this zone. Stored for quick contact lookup during operations. |

**Relationships Involving `zones`:**
- **N:1 with `disasters`** — Many zones belong to one disaster.
- **1:N with `resource_requests`** — A zone can submit many resource requests.
- **1:N with `volunteer_shifts`** — Volunteers are assigned to zones via shifts.
- **N:1 with `shelters`** (via `primary_shelter_id`) — A zone nominates one primary shelter.
- **Row-Level Security (RLS):** Zone Coordinators can only see rows where zone matches their assigned zone (`app.current_zone_id` session variable), enforced transparently by PostgreSQL.

## Group 2: Shelters & Inventory

### Relation 3 — `shelters`

**Relational Schema:**

> shelters(**shelter_id**, name, [address], location_latitude, location_longitude, capacity, current_occupancy°, status)

**Attribute Descriptions:**

| Attribute | Type | Constraints | Description |
|---|---|---|---|
| `shelter_id` | INTEGER | **PRIMARY KEY**, AUTO INCREMENT | Surrogate key uniquely identifying a relief shelter. |
| `name` | VARCHAR(100) | NOT NULL | Descriptive name of the shelter, e.g., *"Government School Hall, Meppadi"* or *"KSRTC Bus Stand Relief Camp"*. |
| `address` | VARCHAR(255) | OPTIONAL | Human-readable physical postal address or landmark description displayed in the UI. |
| `location_latitude` | DOUBLE PRECISION | PART OF composite attribute `location` | Latitude coordinate of the shelter's geographic position. Stored as part of a PostgreSQL **custom composite type** `coordinates(latitude, longitude)` so the entire location is passed as a single structured value to functions. |
| `location_longitude` | DOUBLE PRECISION | PART OF composite attribute `location` | Longitude coordinate. Together with `location_latitude`, allows mapping and proximity-based analysis. |
| `capacity` | INTEGER | NOT NULL, CHECK(capacity > 0) | Maximum number of persons the shelter can safely accommodate. CHECK constraint prevents negative or zero capacity. |
| `current_occupancy` | INTEGER | DEFAULT 0, CHECK(current_occupancy >= 0), **DERIVED°** | Current number of displaced persons at this shelter. **Never manually updated by the application.** The database trigger `trg_auto_update_shelter_occupancy` fires after every INSERT or DELETE on `affected_persons` and automatically recalculates this value — guaranteeing accuracy regardless of which application or user makes changes. |
| `status` | VARCHAR(20) | CHECK(`'operational'`, `'full'`, `'closed'`) | Operational state of the shelter. `'operational'` = accepting persons; `'full'` = at or above capacity; `'closed'` = not available. |

**Relationships Involving `shelters`:**
- **1:N with `affected_persons`** — A shelter houses many displaced persons; each person is at exactly one shelter.
- **1:N with `shelter_inventory`** — A shelter stocks many types of resources (via the M:N junction with `resources`).
- **1:N with `donation_records`** — Donations are received at a specific shelter.
- **Referenced by `distribution_log`** (twice) — As both source and destination of resource transfers.

### Relation 4 — `resource_categories`

**Relational Schema:**

> resource_categories(**category_id**, name, [parent_id\*])

*Self-referencing: `parent_id` → `resource_categories(category_id)`*

**Attribute Descriptions:**

| Attribute | Type | Constraints | Description |
|---|---|---|---|
| `category_id` | INTEGER | **PRIMARY KEY**, AUTO INCREMENT | Surrogate key for the category. |
| `name` | VARCHAR(100) | NOT NULL | Name of the resource category, e.g., *"Medical"*, *"First Aid"*, *"Food"*, *"Water"*, *"Clothing"*. Categories form a named hierarchy that drives roll-up analytics. |
| `parent_id` | INTEGER | NULLABLE, **FK → resource_categories(category_id)** | **Self-referencing Foreign Key** pointing to the parent category in the hierarchy. NULL for top-level (root) categories like *"Medical"* or *"Food"*. A category like *"First Aid"* has `parent_id` pointing to *"Medical"*, and *"Bandages"* points to *"First Aid"*, forming a multi-level tree. Enables hierarchical queries using **recursive CTEs** to sum inventory across entire subtrees. |

**Relationships Involving `resource_categories`:**
- **Self-referencing 1:N** — One parent category can have many child categories; each child has at most one parent. This models an arbitrary-depth tree hierarchy.
- **1:N with `resources`** — Each resource belongs to exactly one category.

---

### Relation 5 — `resources`

**Relational Schema:**

> resources(**resource_id**, name, category_id\*, [unit])

**Attribute Descriptions:**

| Attribute | Type | Constraints | Description |
|---|---|---|---|
| `resource_id` | INTEGER | **PRIMARY KEY**, AUTO INCREMENT | Surrogate key uniquely identifying a resource type in the master catalog. |
| `name` | VARCHAR(100) | NOT NULL | Name of the specific resource item, e.g., *"Paracetamol 500mg"*, *"20L Water Drum"*, *"Rice (1kg packet)"*, *"Woolen Blanket"*. This is the **master catalog** — it defines what a resource is, not how much exists where (that is `shelter_inventory`). |
| `category_id` | INTEGER | NOT NULL, **FK → resource_categories(category_id)** | Foreign key classifying this resource within the hierarchical category tree. NOT NULL because every resource must belong to a category for analytics and roll-up reporting. E.g., *"Paracetamol 500mg"* → category *"Medicines"* → parent *"Medical"*. |
| `unit` | VARCHAR(20) | OPTIONAL | The measurement unit: *"packets"*, *"litres"*, *"pieces"*, *"kg"*. Used in display and reporting to give context to quantities. |

**Relationships Involving `resources`:**
- **N:1 with `resource_categories`** — Many resources belong to one category.
- **M:N with `shelters`** via `shelter_inventory` — A resource can be stocked at many shelters.
- **1:N with `resource_requests`** — A resource can appear in many requests from different zones.
- **1:N with `distribution_log`** — A resource can be transferred many times.

### Relation 6 — `shelter_inventory`

**Relational Schema:**

> shelter_inventory(**shelter_id\***, **resource_id\***, quantity, reorder_level, last_updated)

*Composite Primary Key: (shelter_id, resource_id)*

**Attribute Descriptions:**

| Attribute | Type | Constraints | Description |
|---|---|---|---|
| `shelter_id` | INTEGER | **PK (part)**, **FK → shelters(shelter_id)** | Foreign key identifying the shelter where the resource is stocked. Part of the composite primary key — no shelter can have duplicate entries for the same resource. |
| `resource_id` | INTEGER | **PK (part)**, **FK → resources(resource_id)** | Foreign key identifying which resource is stocked. Together with `shelter_id`, forms the composite PK. |
| `quantity` | INTEGER | NOT NULL, CHECK(quantity >= 0) | Current quantity of this resource at this shelter. CHECK constraint prevents negative stock, which is physically impossible. Updated atomically by `fn_allocate_resources()` during transfers and by UPSERT during donation intake. |
| `reorder_level` | INTEGER | DEFAULT 10 | Minimum quantity threshold. When `quantity` drops below `reorder_level`, the trigger `trg_low_stock_alert` fires and calls `pg_notify('low_stock_alert', ...)` to push a real-time notification to the application via PostgreSQL's `LISTEN/NOTIFY` pub-sub — **no polling required**. |
| `last_updated` | TIMESTAMPTZ | DEFAULT NOW() | Timestamp of the last stock change. Used in reports to track inventory movement patterns. |

**Relationship Description:**  
`shelter_inventory` is a **M:N junction/bridge relation** between `shelters` and `resources`. It resolves the many-to-many relationship: a shelter stocks many resource types, and a resource type can be stocked at many shelters. The composite primary key `(shelter_id, resource_id)` ensures one row per resource-per-shelter, enabling UPSERT semantics on donation intake.

## Group 3: People — ISA Generalization / Specialization

The `people` entity is a **generalized superclass** with two specialization subclasses: `volunteers` and `affected_persons`. This ISA hierarchy is implemented using the **Table-per-Type** mapping: both the superclass and each subclass become separate relations, and the subclass uses the superclass PK as its own PK (and FK simultaneously).

### Relation 7 — `people` (Superclass / Base Table)

**Relational Schema:**

> people(**person_id**, name, [contact], [email])

**Attribute Descriptions:**

| Attribute | Type | Constraints | Description |
|---|---|---|---|
| `person_id` | INTEGER | **PRIMARY KEY**, AUTO INCREMENT | Surrogate key uniquely identifying any person. Shared as the PK by all specializations (`volunteers`, `affected_persons`). |
| `name` | VARCHAR(100) | NOT NULL | Full name of the person. Required for all person records regardless of their role. |
| `contact` | VARCHAR(20) | OPTIONAL | Phone number. Optional because some persons (especially displaced persons in emergencies) may not have a number available at registration time. |
| `email` | VARCHAR(100) | OPTIONAL | Email address. More relevant for volunteers who receive shift notifications. |

> **PostgreSQL Implementation Note:** This base table uses the `INHERITS` keyword. Querying `SELECT * FROM people` returns rows from `people`, `volunteers`, and `affected_persons` combined — a uniquely PostgreSQL feature mirroring OOP class inheritance at the database level.

---

### Relation 8 — `volunteers` (Subclass of `people`)

**Relational Schema:**

> volunteers(**person_id\***, name, [contact], [email], {skills}, [availability], [assigned_zone\*])

*`person_id` is simultaneously the PK of `volunteers` and FK → `people(person_id)`*

**Attribute Descriptions:**

| Attribute | Type | Constraints | Description |
|---|---|---|---|
| `person_id` | INTEGER | **PK**, **FK → people(person_id)** | Inherited from `people`. Serves as the PK of `volunteers`. One-to-one correspondence with a `people` row — a volunteer *is a* person. |
| `name` | VARCHAR(100) | NOT NULL | Inherited from `people`. Full name of the volunteer. |
| `contact` | VARCHAR(20) | OPTIONAL | Inherited from `people`. Phone number. |
| `email` | VARCHAR(100) | OPTIONAL | Inherited from `people`. Email for shift notifications. |
| `skills` | TEXT[] | **{Multivalued attribute}** — PostgreSQL array type | An array of skill tags the volunteer possesses, e.g., `{'first_aid', 'driving', 'cooking', 'translation'}`. Stored using PostgreSQL's native array type, avoiding a separate junction table. Supports set-based queries: `skills @> ARRAY['first_aid']` finds all first-aid-trained volunteers; `skills && ARRAY['driving', 'logistics']` finds volunteers with any overlapping skill. |
| `availability` | TSRANGE | OPTIONAL — PostgreSQL range type | A timestamp range indicating the volunteer's availability window, e.g., `'[2026-07-09 08:00, 2026-07-20 18:00)'`. Range type supports overlap detection (`&&`) and containment (`@>`), enabling queries like "find all volunteers available right now" without manual date comparison. |
| `assigned_zone` | INTEGER | OPTIONAL, **FK → zones(zone_id)** | The zone to which this volunteer is currently assigned. Optional because a volunteer may be registered but not yet assigned to any zone. |

**Relationships Involving `volunteers`:**
- **ISA specialization of `people`** — A volunteer is a specific kind of person with additional attributes.
- **N:1 with `zones`** — Many volunteers can be assigned to one zone.
- **1:N with `volunteer_shifts`** — A volunteer can be assigned to multiple non-overlapping shifts.

### Relation 9 — `affected_persons` (Subclass of `people`)

**Relational Schema:**

> affected_persons(**person_id\***, name, [contact], [email], {medical_needs}, [shelter_id\*], registered_at)

*`person_id` is simultaneously the PK of `affected_persons` and FK → `people(person_id)`*

**Attribute Descriptions:**

| Attribute | Type | Constraints | Description |
|---|---|---|---|
| `person_id` | INTEGER | **PK**, **FK → people(person_id)** | Inherited from `people`. Serves as the PK of `affected_persons`. |
| `name` | VARCHAR(100) | NOT NULL | Inherited from `people`. Full name of the displaced person. |
| `contact` | VARCHAR(20) | OPTIONAL | Inherited from `people`. |
| `email` | VARCHAR(100) | OPTIONAL | Inherited from `people`. |
| `medical_needs` | JSONB | **{Multivalued / Composite attribute}** — stored as JSONB | A JSON document describing the person's specific medical and accessibility needs. JSONB is used because needs vary enormously between individuals and cannot be predicted at schema design time. Example: `{"conditions": ["diabetes", "hypertension"], "medications": ["Metformin"], "wheelchair": true, "oxygen_required": false}`. Supports rich query operators: `WHERE medical_needs @> '{"wheelchair": true}'` finds all persons needing accessible shelters. |
| `shelter_id` | INTEGER | OPTIONAL, **FK → shelters(shelter_id)** | The shelter where this person is currently registered. Optional because a person may be entered before being assigned to a specific shelter. When assigned or removed, the trigger `trg_auto_update_shelter_occupancy` automatically updates `shelters.current_occupancy`. |
| `registered_at` | TIMESTAMPTZ | DEFAULT NOW() | Timestamp of when this person was registered. Used to track registration rates during a disaster's active period. |

**Relationships Involving `affected_persons`:**
- **ISA specialization of `people`** — A displaced person is a specific kind of person.
- **N:1 with `shelters`** — Many displaced persons can be registered at one shelter.

## Group 4: Allocation & Distribution

### Relation 10 — `resource_requests`

**Relational Schema:**

> resource_requests(**request_id**, zone_id\*, resource_id\*, quantity_requested, urgency, priority_score°, status, requested_at, [fulfilled_at])

**Attribute Descriptions:**

| Attribute | Type | Constraints | Description |
|---|---|---|---|
| `request_id` | INTEGER | **PRIMARY KEY**, AUTO INCREMENT | Surrogate key uniquely identifying a resource request. |
| `zone_id` | INTEGER | NOT NULL, **FK → zones(zone_id)** | The zone that submitted this request. NOT NULL because a request must be tied to a specific affected zone. |
| `resource_id` | INTEGER | NOT NULL, **FK → resources(resource_id)** | The specific resource type being requested (e.g., *"20L Water Drum"*). |
| `quantity_requested` | INTEGER | NOT NULL, CHECK(quantity_requested > 0) | How many units the zone needs. Must be positive — a request for zero or negative quantity is semantically invalid. |
| `urgency` | VARCHAR(10) | NOT NULL, CHECK(`'critical'`, `'high'`, `'medium'`, `'low'`) | Zone Coordinator's assessment of how urgently the resource is needed. Constrained to four levels. `'critical'` requests (e.g., drinking water for 500 people) are processed before `'low'` requests (e.g., extra blankets). |
| `priority_score` | INTEGER | **GENERATED COLUMN°** (computed by database) | A numeric score computed automatically by PostgreSQL as a **generated column** expression, combining `urgency` (weights: critical=40, high=30, medium=20, low=10) and `quantity_requested`. The application **never writes this value** — the database recomputes it whenever inputs change. Requests are ranked by this score in the `v_pending_requests_ranked` view so Warehouse Managers always process the most urgent requests first. |
| `status` | VARCHAR(20) | CHECK(`'pending'`, `'fulfilled'`, `'cancelled'`) | Lifecycle state. Starts as `'pending'`. Set to `'fulfilled'` atomically by `fn_allocate_resources()`. Set to `'cancelled'` by the trigger `trg_cascade_disaster_close` when the parent disaster is resolved. |
| `requested_at` | TIMESTAMPTZ | DEFAULT NOW() | Timestamp of submission. Used to measure request response times. |
| `fulfilled_at` | TIMESTAMPTZ | OPTIONAL (NULL until fulfilled) | Timestamp of fulfillment. NULL for pending/cancelled requests. Used to calculate average fulfillment time analytics. |

**Relationships Involving `resource_requests`:**
- **N:1 with `zones`** — Many requests come from one zone.
- **N:1 with `resources`** — Many requests can be for the same resource type.

### Relation 11 — `distribution_log`

**Relational Schema:**

> distribution_log(**log_id**, source_shelter\*, dest_shelter\*, resource_id\*, quantity, distributed_at)

*Table is range-partitioned by `distributed_at` — one child partition per calendar month*

**Attribute Descriptions:**

| Attribute | Type | Constraints | Description |
|---|---|---|---|
| `log_id` | SERIAL | **PRIMARY KEY** | Surrogate key identifying each transfer record. |
| `source_shelter` | INTEGER | NOT NULL, **FK → shelters(shelter_id)** | The shelter from which resources were transferred out. Captures the "from" side of every resource movement. |
| `dest_shelter` | INTEGER | NOT NULL, **FK → shelters(shelter_id)** | The shelter to which resources were transferred. Captures the "to" side. Together with `source_shelter`, enables full traceability of every resource unit across the entire distribution network. |
| `resource_id` | INTEGER | NOT NULL, **FK → resources(resource_id)** | Which resource type was transferred. |
| `quantity` | INTEGER | NOT NULL, CHECK(quantity > 0) | Number of units transferred. Always positive. |
| `distributed_at` | TIMESTAMPTZ | NOT NULL, DEFAULT NOW(), **Partition Key** | Timestamp of transfer. This is the **partition key** — the table is divided into child tables by calendar month (e.g., `distribution_log_2026_07`, `distribution_log_2026_08`) using PostgreSQL native range partitioning. Dramatically improves query performance for time-range queries through **partition pruning** — only the relevant month's partition is scanned. |

**Relationship Description:**  
`distribution_log` records the **historical movement of resources between shelters**. It has two FK references to `shelters` (source and destination), making this a relationship between two shelter instances and a resource. It is an **append-only table** — records are never updated or deleted. The `fn_allocate_resources()` stored function populates this using a `RETURNING` clause in a single round-trip.

### Relation 12 — `volunteer_shifts`

**Relational Schema:**

> volunteer_shifts(**shift_id**, volunteer_id\*, zone_id\*, duty_period)

*GiST Exclusion constraint: `EXCLUDE USING gist (volunteer_id WITH =, duty_period WITH &&)` — no overlapping shifts for the same volunteer*

**Attribute Descriptions:**

| Attribute | Type | Constraints | Description |
|---|---|---|---|
| `shift_id` | INTEGER | **PRIMARY KEY**, AUTO INCREMENT | Surrogate key uniquely identifying a shift assignment. |
| `volunteer_id` | INTEGER | NOT NULL, **FK → volunteers(person_id)** | The volunteer being assigned to this shift. |
| `zone_id` | INTEGER | NOT NULL, **FK → zones(zone_id)** | The zone where the volunteer will be deployed during this shift. |
| `duty_period` | TSRANGE | NOT NULL — PostgreSQL range type | A timestamp range defining when the shift starts and ends, e.g., `'[2026-07-09 08:00, 2026-07-09 20:00)'`. This single attribute captures both start and end. Supports overlap detection via the `&&` operator. |

**Key Constraint — The Exclusion Constraint:**

```sql
EXCLUDE USING gist (volunteer_id WITH =, duty_period WITH &&)
```

This means: *for any two rows, it is forbidden for `volunteer_id` to be equal (same volunteer) AND `duty_period` to overlap (`&&`).* In plain English: **the same volunteer cannot have two overlapping shifts.** This is enforced by a GiST index on every INSERT or UPDATE, guaranteeing at the database level — not application level — that no volunteer is ever double-booked, even in concurrent transactions. This is a uniquely PostgreSQL feature unavailable in MySQL, Oracle, or SQL Server.

**Relationships Involving `volunteer_shifts`:**
- **N:1 with `volunteers`** — A volunteer can have many non-overlapping shifts.
- **N:1 with `zones`** — A zone can have many shifts assigned to it.
- Resolves the **M:N relationship** between `volunteers` and `zones` over time, with `duty_period` as the relationship's own data attribute.

## Group 5: Donations

### Relation 13 — `donation_records`

**Relational Schema:**

> donation_records(**donation_id**, [donor_name], {items}, received_at, [receiving_shelter\*])

**Attribute Descriptions:**

| Attribute | Type | Constraints | Description |
|---|---|---|---|
| `donation_id` | INTEGER | **PRIMARY KEY**, AUTO INCREMENT | Surrogate key uniquely identifying a donation event. |
| `donor_name` | VARCHAR(100) | OPTIONAL | Name of the donating individual or organization, e.g., *"Rotary Club Chennai"*, *"Anonymous"*. Optional because anonymous donations are common in disaster relief. |
| `items` | JSONB | **{Multivalued / Composite attribute}** | A JSON array describing all items in this donation: `[{"resource_id": 5, "quantity": 100}, {"resource_id": 8, "quantity": 50}]`. JSONB is used because donation compositions vary wildly and often include many different items in a single delivery. When processed, the application iterates this array and performs an UPSERT on `shelter_inventory` for each item — if the resource already exists at the shelter, the quantity is added; otherwise, a new row is inserted. |
| `received_at` | TIMESTAMPTZ | DEFAULT NOW() | Timestamp of when the donation was physically received and logged. Used for reporting donation trends over time. |
| `receiving_shelter` | INTEGER | OPTIONAL, **FK → shelters(shelter_id)** | The shelter at which the donation was delivered. Optional to handle cases where donations are recorded before a specific shelter destination is determined. |

**Relationships Involving `donation_records`:**
- **N:1 with `shelters`** — Many donations can be received at one shelter.
- **No direct FK to `shelter_inventory`** — the relationship is procedural: when a donation is recorded, the application unpacks `items` JSONB and performs UPSERT operations on `shelter_inventory`, keeping `donation_records` as an immutable audit record.

## Group 6: Audit

### Relation 14 — `audit_log`

**Relational Schema:**

> audit_log(**log_id**, table_name, operation, [old_values], [new_values], [changed_by], changed_at)

*This table is never written to by application code — populated entirely by the database trigger `trg_audit_log`.*

**Attribute Descriptions:**

| Attribute | Type | Constraints | Description |
|---|---|---|---|
| `log_id` | INTEGER | **PRIMARY KEY**, AUTO INCREMENT | Surrogate key for each audit event. |
| `table_name` | VARCHAR(50) | NOT NULL | The name of the table that was modified, e.g., `'resource_requests'`, `'shelter_inventory'`. Identifies the context of every mutation. |
| `operation` | VARCHAR(10) | NOT NULL, CHECK(`'INSERT'`, `'UPDATE'`, `'DELETE'`) | The type of data modification that occurred. |
| `old_values` | JSONB | OPTIONAL (NULL for INSERT) | A JSONB snapshot of the entire row **before** the change. NULL for INSERT operations (no previous state). Captured by the trigger using `OLD.*`. |
| `new_values` | JSONB | OPTIONAL (NULL for DELETE) | A JSONB snapshot of the entire row **after** the change. NULL for DELETE operations. Captured using `NEW.*`. Together with `old_values`, enables **full diff reconstruction** of any data change at any point in time. |
| `changed_by` | VARCHAR(100) | OPTIONAL | The PostgreSQL session user (`session_user`) at the time of the change, automatically captured by the trigger. Identifies which database role made the change. |
| `changed_at` | TIMESTAMPTZ | DEFAULT NOW() | Precise timestamp of the mutation. Auto-populated by the trigger. |

**Key Design Principle:**  
This table is an **insert-only, append-only relation**. No application code is authorized to write to it — only the database trigger `trg_audit_log` does so. This guarantees the audit trail cannot be tampered with by application bugs or actors who gain application-level access. It satisfies project objective O7 (Comprehensive Audit Trail) without any application code.

## Complete Relational Schema Summary

```
R1:  disasters(disaster_id, name, type, severity, active_period, status, created_at)
     PK: disaster_id

R2:  zones(zone_id, disaster_id*, name, severity, [primary_shelter_id*], [coordinator_contact])
     PK: zone_id
     FK: disaster_id → disasters(disaster_id)
     FK: primary_shelter_id → shelters(shelter_id)

R3:  shelters(shelter_id, name, [address], location_latitude, location_longitude, capacity, current_occupancy°, status)
     PK: shelter_id
     DERIVED: current_occupancy (maintained by trigger)

R4:  resource_categories(category_id, name, [parent_id*])
     PK: category_id
     FK: parent_id → resource_categories(category_id)  [self-referencing]

R5:  resources(resource_id, name, category_id*, [unit])
     PK: resource_id
     FK: category_id → resource_categories(category_id)

R6:  shelter_inventory(shelter_id*, resource_id*, quantity, reorder_level, last_updated)
     PK: (shelter_id, resource_id)  [composite]
     FK: shelter_id → shelters(shelter_id)
     FK: resource_id → resources(resource_id)

R7:  people(person_id, name, [contact], [email])
     PK: person_id
     [Superclass — ISA hierarchy base]

R8:  volunteers(person_id*, name, [contact], [email], {skills}, [availability], [assigned_zone*])
     PK: person_id
     FK: person_id → people(person_id)  [ISA subclass PK = FK]
     FK: assigned_zone → zones(zone_id)
     MULTIVALUED: skills (TEXT[] array)

R9:  affected_persons(person_id*, name, [contact], [email], {medical_needs}, [shelter_id*], registered_at)
     PK: person_id
     FK: person_id → people(person_id)  [ISA subclass PK = FK]
     FK: shelter_id → shelters(shelter_id)
     MULTIVALUED: medical_needs (JSONB document)

R10: resource_requests(request_id, zone_id*, resource_id*, quantity_requested, urgency, priority_score°, status, requested_at, [fulfilled_at])
     PK: request_id
     FK: zone_id → zones(zone_id)
     FK: resource_id → resources(resource_id)
     DERIVED: priority_score (PostgreSQL generated column)

R11: distribution_log(log_id, source_shelter*, dest_shelter*, resource_id*, quantity, distributed_at)
     PK: log_id
     FK: source_shelter → shelters(shelter_id)
     FK: dest_shelter → shelters(shelter_id)
     FK: resource_id → resources(resource_id)
     PARTITION KEY: distributed_at (range partitioned by month)

R12: volunteer_shifts(shift_id, volunteer_id*, zone_id*, duty_period)
     PK: shift_id
     FK: volunteer_id → volunteers(person_id)
     FK: zone_id → zones(zone_id)
     EXCL: EXCLUDE USING gist (volunteer_id WITH =, duty_period WITH &&)

R13: donation_records(donation_id, [donor_name], {items}, received_at, [receiving_shelter*])
     PK: donation_id
     FK: receiving_shelter → shelters(shelter_id)
     MULTIVALUED: items (JSONB array of resource-quantity pairs)

R14: audit_log(log_id, table_name, operation, [old_values], [new_values], [changed_by], changed_at)
     PK: log_id
     [Trigger-populated only — never written by application code]
```

**Notation Legend:**
- Plain text = Primary Key attributes  ← Underlined in formal notation
- attribute\* = Foreign Key
- {attribute} = Multivalued (array or JSONB)
- attribute° = Derived / Auto-generated
- [attribute] = Nullable / Optional

## Relationship Summary Table

| Relationship | Cardinality | Entities | FK Location | Business Meaning |
|---|---|---|---|---|
| Disaster → Zones | 1:N | `disasters`, `zones` | `zones.disaster_id` | A disaster spawns one or more affected geographic zones |
| Zone → Primary Shelter | N:1 | `zones`, `shelters` | `zones.primary_shelter_id` | Each zone nominates one shelter as its main relief camp |
| Resource → Category | N:1 | `resources`, `resource_categories` | `resources.category_id` | Every resource belongs to one category in the hierarchy |
| Category → Category | 1:N (self-ref) | `resource_categories` | `resource_categories.parent_id` | Categories form an arbitrary-depth tree hierarchy |
| Shelter ↔ Resource | M:N | `shelters`, `resources` | Via `shelter_inventory` (junction) | Shelters stock multiple resource types; resources appear at multiple shelters |
| Volunteer ISA Person | ISA | `people`, `volunteers` | `volunteers.person_id` | A volunteer is a specialized kind of person |
| Affected Person ISA Person | ISA | `people`, `affected_persons` | `affected_persons.person_id` | A displaced person is a specialized kind of person |
| Affected Person → Shelter | N:1 | `affected_persons`, `shelters` | `affected_persons.shelter_id` | Many displaced persons live at one shelter |
| Volunteer → Zone | N:1 | `volunteers`, `zones` | `volunteers.assigned_zone` | A volunteer is assigned to work in one zone |
| Request → Zone | N:1 | `resource_requests`, `zones` | `resource_requests.zone_id` | Resource requests originate from specific zones |
| Request → Resource | N:1 | `resource_requests`, `resources` | `resource_requests.resource_id` | Each request is for one type of resource |
| Shift → Volunteer | N:1 | `volunteer_shifts`, `volunteers` | `volunteer_shifts.volunteer_id` | A volunteer can have many (non-overlapping) shifts |
| Shift → Zone | N:1 | `volunteer_shifts`, `zones` | `volunteer_shifts.zone_id` | A shift is assigned to a specific zone |
| Distribution → Source Shelter | N:1 | `distribution_log`, `shelters` | `distribution_log.source_shelter` | Each transfer record has a source shelter |
| Distribution → Dest Shelter | N:1 | `distribution_log`, `shelters` | `distribution_log.dest_shelter` | Each transfer record has a destination shelter |
| Distribution → Resource | N:1 | `distribution_log`, `resources` | `distribution_log.resource_id` | Each transfer moves one type of resource |
| Donation → Shelter | N:1 | `donation_records`, `shelters` | `donation_records.receiving_shelter` | Donations are delivered to a specific shelter |
