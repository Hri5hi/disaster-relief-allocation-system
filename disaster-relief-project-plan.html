DBMS Course Project — PostgreSQL

Disaster Relief Resource Allocation System

A relief coordination platform where shelters, volunteers, donations, and supplies are tracked and matched to zones in need — with almost all of the intelligence living inside PostgreSQL instead of in application code.

Critical — must ship High — strongly recommended Medium — good to have Stretch — if time allows
01

What you're actually building

In plain terms, before any SQL: imagine a hurricane hits a coastline. Several shelters open up. Each one has some food, water, and medicine — but never the right amount in the right place. Volunteers show up and need to be assigned somewhere. Donations pour in. Someone has to decide, minute by minute, which shelter sends its spare blankets to which other shelter that's run out. That decision-making — not the pretty screens around it — is the database.

🏚️ The problem it solves

Relief coordinators need to know: which zones are short on what, which shelters have surplus, who's available to move supplies, and who's already been helped. Right now that's usually a spreadsheet. You're replacing the spreadsheet with a real database that enforces its own rules.

🧠 Where the "brain" lives

In your old hostel project, Java decided everything and the database just stored rows. Here it flips: PostgreSQL functions decide whether an allocation is valid, triggers keep inventory numbers correct automatically, and constraints make certain bad states physically impossible to insert.

🎯 Why evaluators like this topic

It naturally needs multi-table transactions (move stock from A to B safely), priority ranking (who gets help first), hierarchical data (resource categories), and real-time alerts (low stock) — all textbook DBMS material, none of it forced.

Beginner reassurance: you do not need to know PostgreSQL yet to start this. Section 02 below teaches every concept you'll touch, in plain English, with a two-line example each. You'll pick it up as you build rather than needing to "learn Postgres first."
02

PostgreSQL, explained for a beginner

Every concept below shows up somewhere in this project. Read this once before you touch the schema — it'll make every later section click into place.

📋 Tables & keys

A table is a spreadsheet with strict rules. Every row needs a unique ID (PRIMARY KEY). When one table points to a row in another (a shelter "belongs to" a zone), that's a FOREIGN KEY — it stops you from linking to something that doesn't exist.

CREATE TABLE shelters (
  shelter_id SERIAL PRIMARY KEY,
  zone_id INTEGER REFERENCES zones(zone_id)
);

🔗 JOINs

Real data lives in separate tables (shelters, resources, zones). A JOIN stitches them back together for a query — e.g. "show me every shelter with its zone name" in one result, instead of two round trips from Java.

SELECT s.name, z.name
FROM shelters s
JOIN zones z ON s.zone_id = z.zone_id;

🔒 CHECK constraints

A rule the database enforces on every row, forever, no matter what inserts it — Java, a script, or you typing directly into psql. If you say quantity must be positive, the database itself refuses negative stock.

quantity INTEGER CHECK (quantity >= 0),
urgency TEXT CHECK (urgency IN
  ('critical','high','medium','low'))

⚙️ Stored functions / procedures

Instead of Java doing "check stock → deduct → insert log → mark fulfilled" in four separate trips to the database, you write one PL/pgSQL function that does all four steps atomically inside Postgres. Java just calls it.

SELECT * FROM
  fn_allocate_resources(
    request_id, source_shelter);
-- one call, everything happens inside

🔔 Triggers

Code that runs automatically whenever something happens to a table — no one has to remember to call it. "Whenever stock drops below the reorder level, insert an alert" is a trigger, not something Java has to check.

CREATE TRIGGER trg_low_stock
AFTER UPDATE ON shelter_inventory
FOR EACH ROW EXECUTE FUNCTION
  fn_notify_low_stock();

🧾 Transactions

A group of steps that must all succeed or all fail together — never half-done. Moving 50 blankets from Shelter A to Shelter B is two updates; a transaction guarantees you never end up with the blankets "gone" from A but never arrived at B.

BEGIN;
  UPDATE ... -- deduct from source
  UPDATE ... -- add to destination
COMMIT;

👁️ Views & materialized views

A view is a saved query you can treat like a table — e.g. v_urgent_pending_requests always shows current urgent requests. A materialized view is the same idea but the result is physically stored and refreshed on a schedule, for expensive reports.

CREATE VIEW v_low_stock AS
SELECT * FROM shelter_inventory
WHERE quantity < reorder_level;

🗂️ JSONB

For data that doesn't fit neat columns — a volunteer's skills, a person's medical needs — Postgres lets you store flexible JSON in a column and still search inside it efficiently.

medical_needs JSONB;
-- {"conditions":["asthma"],"wheelchair":true}
WHERE medical_needs @> '{"wheelchair":true}'

📦 Arrays

A single column that holds a list — a volunteer's skills can just be TEXT[] instead of a whole separate table, when the list is short and simple.

skills TEXT[];
WHERE 'first_aid' = ANY(skills)

⏱️ Range types + exclusion constraints

A column that stores a start-and-end span (a volunteer's shift) as one value. An exclusion constraint then makes overlapping shifts for the same volunteer impossible to insert — the database rejects it, no Java validation needed.

duty_period tsrange,
EXCLUDE USING gist (
  volunteer_id WITH =,
  duty_period WITH &&)

📊 Window functions

Ranking or running calculations "over a window" of rows without collapsing them into one — e.g. rank requests by urgency within each zone, or compute a 7-day rolling average, while still seeing every individual row.

ROW_NUMBER() OVER (
  PARTITION BY zone_id
  ORDER BY urgency DESC)

🌳 Recursive CTEs

A query that refers to itself to walk a hierarchy — e.g. "Medical → First Aid → Bandages" — rolling quantities up from the leaves to the top category in one query instead of a loop in Java.

Where the logic lives

This is the single biggest mindset shift from your last project. Compare the old way to the new way — this is what an evaluator is actually grading you on.

Old pattern

App does the thinking

  • Check if shelter has stock — in Java
  • Count current occupants — in Java
  • Build the allocation object — in Java
  • Database is just a filing cabinet
  • 4–5 separate round trips per action
→
This project

Database does the thinking

  • One function call: fn_allocate_resources()
  • Stock check, deduction, logging happen inside Postgres
  • Triggers auto-update inventory + raise alerts
  • Constraints make invalid states impossible
  • App layer just displays what comes back
Note on the app layer: whether you keep the existing JavaFX shell, rebuild it as a simple web app, or use a CLI is a secondary decision — the grading weight is in the schema, functions, triggers, and constraints described below. Pick whichever front end lets you spend the least extra time so more of it goes into the database work.

Build roadmap

A sensible build order — each phase produces something demoable, so you're never stuck with "half a schema and nothing that runs."

01
~1 day

Core schema + relationships

  • Create people/volunteers/affected_persons with inheritance
  • Create disasters, disaster_zones, shelters, resources
  • Add primary/foreign keys, basic CHECK constraints, seed data
02
~1 day

Inventory & requests

  • Add shelter_inventory, resource_requests, resource_categories
  • Write plain CRUD queries and confirm JOINs return sensible results
  • Add the recursive CTE for category roll-up
03
~2 days

Stored functions — the core logic

  • fn_allocate_resources() — the flagship transaction
  • fn_zone_deficit_report() — deficit/urgency query

~1 day

  • Audit log trigger across key tables
  • Occupancy auto-update, disaster-resolved cascade

~1 day

Views, ranking & analytics

  • Dashboard views (occupancy, pending requests, active disasters)
  • Window-function priority ranking and trend queries
  • Materialized views for consumption summaries

~1 day
