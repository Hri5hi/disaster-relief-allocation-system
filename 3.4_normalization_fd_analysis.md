## Notation Guide

| Symbol | Meaning |
|---|---|
| X → Y | X functionally determines Y |
| X →→ Y | X multi-valued determines Y (MVD) |
| X⁺ | Attribute closure of X under a given FD set F |
| {A}⁺ = R | {A} is a superkey of relation R |
| CK | Candidate Key — a minimal superkey |
| PK | Primary Key — the chosen candidate key |
| NF | Normal Form |
| BCNF | Boyce–Codd Normal Form |

---

## 1. Theoretical Basis

A **Functional Dependency (FD)** X → Y holds on relation R if, for any two tuples t₁ and t₂ in R, whenever t₁[X] = t₂[X], it follows that t₁[Y] = t₂[Y]. In plain terms: knowing X is sufficient to uniquely determine Y.

**Armstrong's Axioms** (used for computing attribute closures):
1. **Reflexivity:** If Y ⊆ X, then X → Y
2. **Augmentation:** If X → Y, then XZ → YZ for any Z
3. **Transitivity:** If X → Y and Y → Z, then X → Z

**Normal forms addressed:**
- **1NF:** Every attribute value is atomic; no repeating groups
- **2NF:** 1NF + no non-key attribute has a *partial* dependency on any candidate key
- **3NF:** 2NF + no non-key attribute has a *transitive* dependency on any candidate key
- **BCNF:** For every non-trivial FD X → Y, X must be a superkey of the relation

## 2. Functional Dependency Identification — All 14 Relations

### R1 — `disasters(disaster_id, name, type, severity, active_period, status, created_at)`

**FD Set F₁:**
- **F1.1:** `disaster_id → name, type, severity, active_period, status, created_at`

**Significance:** `disaster_id` is a surrogate key auto-incremented by the database. It is the sole determinant. No non-key attribute determines any other — `type` (e.g., `'flood'`) does not determine `severity`; two flood disasters may have different severities. `active_period` is a PostgreSQL `DATERANGE` encoding start and end date as a single structured attribute; it is fully determined by `disaster_id` and is not decomposable into separate FDs.

---

### R2 — `zones(zone_id, disaster_id, name, severity, primary_shelter_id, coordinator_contact)`

**FD Set F₂:**
- **F2.1:** `zone_id → disaster_id, name, severity, primary_shelter_id, coordinator_contact`

**Significance:** `zone_id` is the sole surrogate key. `disaster_id` is a FK reference, not a determinant of zone attributes — one disaster can have many zones with different severities and coordinators. `coordinator_contact` is an operational contact number; it does not functionally determine the zone (a coordinator may change), so it is **not** a candidate key.

---

### R3 — `shelters(shelter_id, name, address, location, capacity, current_occupancy, status)`

**FD Set F₃:**
- **F3.1:** `shelter_id → name, address, location, capacity, current_occupancy, status`

**Significance:** `current_occupancy` is a **trigger-maintained derived attribute** (`trg_auto_update_shelter_occupancy`). Its true FD is:  
`shelter_id → current_occupancy` **via** COUNT of `affected_persons` where `shelter_id` matches.  
Although `address` and `location` describe the same physical place, `address → location` is **not** treated as an FD in this schema — location coordinates may be null (offline registration), and two shelters at the same address (e.g., different halls within one building) would break this dependency. They are kept as independent attributes.

---

### R4 — `resource_categories(category_id, name, parent_id)`

**FD Set F₄:**
- **F4.1:** `category_id → name, parent_id`

**Significance:** The `parent_id` self-referencing FK models an arbitrary-depth category tree (e.g., *Medical → First Aid → Bandages*). Although `parent_id` references the same relation's PK, it is not a determinant — a parent category does not determine the names of its children. `name` is **not** a candidate key: the same name (e.g., `'Other'`) could legitimately appear under different parent categories.

---

### R5 — `resources(resource_id, name, category_id, unit)`

**FD Set F₅:**
- **F5.1:** `resource_id → name, category_id, unit`

**Significance:** `category_id` is a FK — it classifies the resource but does not determine its `name` or `unit` (a category contains many resources). `unit` is determined by `resource_id`, not by `category_id` (two resources in the same category may use different units — e.g., *Paracetamol* uses `'tablets'` while *Antiseptic Lotion* uses `'ml'`).

---

### R6 — `shelter_inventory(shelter_id, resource_id, quantity, reorder_level, last_updated)`

**FD Set F₆:**
- **F6.1:** `(shelter_id, resource_id) → quantity, reorder_level, last_updated`
- **F6.2:** `shelter_id ↛ quantity` *(shelter_id alone does not determine quantity — a shelter stores many resources at different quantities)*
- **F6.3:** `resource_id ↛ quantity` *(resource_id alone does not determine quantity — a resource appears at many shelters with different stock levels)*

**Significance:** This is the most important relation for normalization analysis. The composite key `(shelter_id, resource_id)` is the **minimal** determinant for all non-key attributes. Neither component alone is sufficient. `reorder_level` is set per shelter-per-resource pair (different shelters may have different reorder thresholds for the same resource), confirming full dependence on the composite key.

---

### R7 — `people(person_id, name, contact, email)`

**FD Set F₇:**
- **F7.1:** `person_id → name, contact, email`

**Significance:** `contact` and `email` are optional attributes and are **not** candidate keys — they may be null (emergency registrations) and are not enforced as UNIQUE at the database level. Thus neither `{contact}` nor `{email}` can functionally determine `person_id` in general.

---

### R8 — `volunteers(person_id, name, contact, email, skills, availability, assigned_zone)`

**FD Set F₈:**
- **F8.1:** `person_id → name, contact, email, skills, availability, assigned_zone`

**Significance:** `skills` is a **multivalued attribute** stored as `TEXT[]`. In strict relational theory, a set-valued attribute creates a **Multi-Valued Dependency (MVD)**: `person_id →→ skills`. This is a 4NF concern addressed separately in §5. `assigned_zone` is a FK to `zones`, fully determined by `person_id` — a volunteer has exactly one assigned zone at any time.

---

### R9 — `affected_persons(person_id, name, contact, email, medical_needs, shelter_id, registered_at)`

**FD Set F₉:**
- **F9.1:** `person_id → name, contact, email, medical_needs, shelter_id, registered_at`

**Significance:** `medical_needs` is a `JSONB` document encoding variable-structure medical data. It is fully determined by `person_id` (a person has one medical profile). `shelter_id` is determined by `person_id` — a displaced person resides at exactly one shelter at registration time.

---

### R10 — `resource_requests(request_id, zone_id, resource_id, quantity_requested, urgency, priority_score, status, requested_at, fulfilled_at)`

**FD Set F₁₀:**
- **F10.1:** `request_id → zone_id, resource_id, quantity_requested, urgency, priority_score, status, requested_at, fulfilled_at`
- **F10.2:** `(urgency, quantity_requested) → priority_score`

**Significance of F10.2:** `priority_score` is a **PostgreSQL GENERATED COLUMN** computed as:  
```
priority_score = CASE urgency
    WHEN 'critical' THEN 40
    WHEN 'high'     THEN 30
    WHEN 'medium'   THEN 20
    WHEN 'low'      THEN 10
END + quantity_requested
```
This creates a transitive dependency chain: `request_id → urgency`, `request_id → quantity_requested`, and `(urgency, quantity_requested) → priority_score`. The full normalization implications are analysed in **Case Study 3** (§4.3).

---

### R11 — `distribution_log(log_id, source_shelter, dest_shelter, resource_id, quantity, distributed_at)`

**FD Set F₁₁:**
- **F11.1:** `log_id → source_shelter, dest_shelter, resource_id, quantity, distributed_at`

**Significance:** This is an **append-only audit table**. Each row is an immutable transfer record. `source_shelter` does not determine `dest_shelter` (a source shelter transfers to many destinations); `resource_id` does not determine `quantity` (the same resource is transferred in different amounts on different occasions). `log_id` is the sole determinant.

---

### R12 — `volunteer_shifts(shift_id, volunteer_id, zone_id, duty_period)`

**FD Set F₁₂:**
- **F12.1:** `shift_id → volunteer_id, zone_id, duty_period`
- **F12.2:** `(volunteer_id, duty_period) → shift_id, zone_id`

**Significance:** F12.2 arises from the **GiST exclusion constraint** `EXCLUDE USING gist (volunteer_id WITH =, duty_period WITH &&)`, which guarantees no two rows have the same volunteer with overlapping time ranges. If two records have the same `volunteer_id` and an identical (non-overlapping) `duty_period`, they are in fact the same shift. Therefore `{volunteer_id, duty_period}` is an **alternate candidate key**. This relation has **two candidate keys**, making BCNF analysis more interesting (see §4 discussion).

---

### R13 — `donation_records(donation_id, donor_name, items, received_at, receiving_shelter)`

**FD Set F₁₃:**
- **F13.1:** `donation_id → donor_name, items, received_at, receiving_shelter`

**Significance:** `donor_name` is informational — the same donor (e.g., *Rotary Club Chennai*) can make multiple donations, so `donor_name` does **not** determine `donation_id`. `receiving_shelter` is a FK; it does not determine other attributes (a shelter receives many donations). `items` is a `JSONB` array; its content is fully determined by the specific donation event (`donation_id`).

---

### R14 — `audit_log(log_id, table_name, operation, old_values, new_values, changed_by, changed_at)`

**FD Set F₁₄:**
- **F14.1:** `log_id → table_name, operation, old_values, new_values, changed_by, changed_at`

**Significance:** Each audit row is an immutable snapshot of one database mutation. `table_name` does not determine `operation` (the same table can be INSERTed into, UPDATEd, or DELETEd). `changed_by` does not determine `table_name` (a user may modify many tables). The surrogate `log_id` is the sole determinant.

## 3. Candidate Key Identification — Attribute Closure Proofs

### 3.1 R6 — `shelter_inventory` (Composite Key Justification)

**Attributes:** {shelter_id, resource_id, quantity, reorder_level, last_updated}  
**FD Set:** F6.1, F6.2, F6.3

**Claim:** {shelter_id, resource_id} is the only candidate key.

**Closure computation:**

```
{shelter_id}⁺:
  Apply F6.1: (shelter_id, resource_id) → ... : shelter_id alone cannot trigger F6.1
  {shelter_id}⁺ = {shelter_id}   ≠ R6  →  NOT a superkey

{resource_id}⁺:
  Apply F6.1: resource_id alone cannot trigger F6.1
  {resource_id}⁺ = {resource_id}  ≠ R6  →  NOT a superkey

{shelter_id, resource_id}⁺:
  Apply F6.1: (shelter_id, resource_id) → quantity, reorder_level, last_updated
  {shelter_id, resource_id}⁺ = {shelter_id, resource_id, quantity, reorder_level, last_updated}
                              = R6  →  SUPERKEY

Minimality check:
  Remove shelter_id: {resource_id}⁺ ≠ R6  →  shelter_id cannot be removed
  Remove resource_id: {shelter_id}⁺ ≠ R6  →  resource_id cannot be removed
  ∴ {shelter_id, resource_id} is MINIMAL  →  CANDIDATE KEY ✅
```

---

### 3.2 R10 — `resource_requests` (Single vs Composite Key)

**Attributes:** {request_id, zone_id, resource_id, quantity_requested, urgency, priority_score, status, requested_at, fulfilled_at}  
**FD Set:** F10.1, F10.2

**Claim:** {request_id} is the only candidate key.

```
{request_id}⁺:
  Apply F10.1: request_id → zone_id, resource_id, quantity_requested, urgency,
                             priority_score, status, requested_at, fulfilled_at
  {request_id}⁺ = {all attributes} = R10  →  SUPERKEY
  Trivially minimal (single attribute)  →  CANDIDATE KEY ✅

Could {zone_id, resource_id} be a candidate key?
  A zone can request the same resource multiple times (once per shortage event).
  So (zone_id, resource_id) does NOT uniquely identify a request.
  {zone_id, resource_id}⁺ = {zone_id, resource_id}  ≠ R10  →  NOT a superkey ✗
```

---

### 3.3 R12 — `volunteer_shifts` (Two Candidate Keys)

**Attributes:** {shift_id, volunteer_id, zone_id, duty_period}  
**FD Set:** F12.1, F12.2

```
{shift_id}⁺:
  Apply F12.1: shift_id → volunteer_id, zone_id, duty_period
  {shift_id}⁺ = {shift_id, volunteer_id, zone_id, duty_period} = R12  →  SUPERKEY
  Minimal  →  CK₁ ✅

{volunteer_id, duty_period}⁺:
  Apply F12.2: (volunteer_id, duty_period) → shift_id, zone_id
  {volunteer_id, duty_period}⁺ = {volunteer_id, duty_period, shift_id, zone_id} = R12  →  SUPERKEY
  Remove volunteer_id: {duty_period}⁺ = {duty_period} ≠ R12
  Remove duty_period:  {volunteer_id}⁺ = {volunteer_id} ≠ R12
  Minimal  →  CK₂ ✅

∴ R12 has two candidate keys: {shift_id} (PK) and {volunteer_id, duty_period} (alternate CK)
```

---

### 3.4 R7 — `people` (Why contact and email are not Candidate Keys)

```
{contact}⁺:
  contact is NULLABLE → cannot be a CK (NULL ≠ NULL in SQL uniqueness)
  Even if non-null: no FD in F₇ has contact as a determinant
  {contact}⁺ = {contact}  ≠ R7  →  NOT a superkey

{email}⁺:
  Same argument — nullable, no FD with email as determinant
  {email}⁺ = {email}  ≠ R7  →  NOT a superkey

{person_id}⁺:
  Apply F7.1: person_id → name, contact, email
  {person_id}⁺ = R7  →  SUPERKEY and CANDIDATE KEY ✅
```

## 4. Normalization Case Studies

The following three case studies demonstrate the step-by-step normalization process, starting from hypothetical unnormalized designs and arriving at the BCNF-compliant relations in the final schema.

---

### 4.1 Case Study 1 — Shelter Resource Stock
**From Unnormalized Naive Design → BCNF**  
*(Covers R3, R4, R5, R6)*

#### Step 0 — Naive Universal Relation

Imagine a single flat table storing all shelter-resource stock information:

```
naive_stock(
    shelter_name, shelter_address,
    resource_name, resource_unit,
    category_name, parent_category_name,
    quantity, reorder_level
)
```

**Sample data showing anomalies:**

| shelter_name | shelter_address | resource_name | resource_unit | category_name | parent_category_name | quantity | reorder_level |
|---|---|---|---|---|---|---|---|
| Meppadi School | Meppadi, Wayanad | Paracetamol 500mg | tablets | Medicines | Medical | 500 | 50 |
| Meppadi School | Meppadi, Wayanad | 20L Water Drum | litres | Water | Essentials | 20 | 5 |
| Kalpetta Hall | Kalpetta, Wayanad | Paracetamol 500mg | tablets | Medicines | Medical | 200 | 30 |

**Anomalies visible:**
- **Update anomaly:** Changing the address of *Meppadi School* requires updating multiple rows
- **Insertion anomaly:** Cannot add a new resource type without having a shelter stocking it
- **Deletion anomaly:** Deleting the last stock row for a shelter removes the shelter's address information

**FD Set for naive_stock:**

| FD | Dependency | Type |
|---|---|---|
| FD-a | `(shelter_name, resource_name) → quantity, reorder_level` | Full dependency on composite key |
| FD-b | `shelter_name → shelter_address` | **PARTIAL** — depends only on left part of key |
| FD-c | `resource_name → resource_unit, category_name` | **PARTIAL** — depends only on right part of key |
| FD-d | `category_name → parent_category_name` | **TRANSITIVE** — via resource_name |

**Candidate key of naive_stock:** `{shelter_name, resource_name}`

---

#### Step 1 — First Normal Form (1NF)

**Check:** Are all attribute values atomic?

✅ All attributes in `naive_stock` are single-valued and atomic. The relation is **already in 1NF**.

> Note: Had we stored multiple resources per row as a comma-separated string (e.g., `"Paracetamol, Bandages"`), that would violate 1NF. The row-per-resource design avoids this.

---

#### Step 2 — Second Normal Form (2NF)

**Violation check:** Does every non-key attribute fully depend on the entire candidate key `{shelter_name, resource_name}`?

- `shelter_address` depends only on `shelter_name` → **PARTIAL DEPENDENCY** ❌
- `resource_unit` depends only on `resource_name` → **PARTIAL DEPENDENCY** ❌
- `category_name` depends only on `resource_name` → **PARTIAL DEPENDENCY** ❌
- `parent_category_name` depends only on `resource_name` (via `category_name`) → **PARTIAL + TRANSITIVE** ❌

**naive_stock is NOT in 2NF.**

**Decomposition to eliminate partial dependencies:**

Remove all partially dependent attributes into their own relations:

```
R_shelters_raw(shelter_name, shelter_address)
    PK: {shelter_name}
    FDs: shelter_name → shelter_address

R_resources_raw(resource_name, resource_unit, category_name, parent_category_name)
    PK: {resource_name}
    FDs: resource_name → resource_unit, category_name
         category_name → parent_category_name  ← transitive, still present!

R_stock_2NF(shelter_name, resource_name, quantity, reorder_level)
    PK: {shelter_name, resource_name}
    FDs: (shelter_name, resource_name) → quantity, reorder_level
```

✅ `R_stock_2NF` is in 2NF (composite PK, all non-key attributes fully depend on it).  
✅ `R_shelters_raw` is in 2NF (single-attribute PK, no partial deps possible).  
⚠️ `R_resources_raw` is in 2NF but **not yet in 3NF** — transitive dependency remains.

---

#### Step 3 — Third Normal Form (3NF)

**Violation check on `R_resources_raw`:**

- `resource_name → category_name` (direct)
- `category_name → parent_category_name` (direct)
- Therefore: `resource_name → parent_category_name` (**TRANSITIVE**) ❌

**`R_resources_raw` is NOT in 3NF** because `parent_category_name` is transitively dependent on `resource_name` via `category_name`, and `category_name` is not a candidate key.

**Decomposition to eliminate transitive dependency:**

```
R_resources_3NF(resource_name, resource_unit, category_name)
    PK: {resource_name}
    FDs: resource_name → resource_unit, category_name
    ✅ In 3NF — no transitive deps remain

R_categories_3NF(category_name, parent_category_name)
    PK: {category_name}
    FDs: category_name → parent_category_name
    ✅ In 3NF
```

All four relations after 3NF decomposition:

| Relation | PK | 3NF? |
|---|---|---|
| `R_shelters_raw(shelter_name, shelter_address)` | `{shelter_name}` | ✅ |
| `R_categories_3NF(category_name, parent_category_name)` | `{category_name}` | ✅ |
| `R_resources_3NF(resource_name, resource_unit, category_name*)` | `{resource_name}` | ✅ |
| `R_stock_2NF(shelter_name*, resource_name*, quantity, reorder_level)` | `{shelter_name, resource_name}` | ✅ |

---

#### Step 4 — Boyce–Codd Normal Form (BCNF)

**BCNF check:** For every non-trivial FD X → Y, is X a superkey?

| Relation | FD | Determinant X | X is superkey? | BCNF? |
|---|---|---|---|---|
| `R_shelters_raw` | `shelter_name → shelter_address` | `{shelter_name}` (PK) | ✅ | ✅ |
| `R_categories_3NF` | `category_name → parent_category_name` | `{category_name}` (PK) | ✅ | ✅ |
| `R_resources_3NF` | `resource_name → resource_unit, category_name` | `{resource_name}` (PK) | ✅ | ✅ |
| `R_stock_2NF` | `(shelter_name, resource_name) → quantity, reorder_level` | `{shelter_name, resource_name}` (PK) | ✅ | ✅ |

**All four relations are in BCNF.**

#### Step 5 — Final Schema Mapping (Surrogate Keys)

The 3NF/BCNF-compliant relations above use natural keys (names). In the final schema, surrogate integer PKs replace natural keys to avoid string-comparison costs and handle name changes:

```
R3:  shelters(shelter_id, name, address, location, capacity, current_occupancy°, status)
R4:  resource_categories(category_id, name, parent_id*)
R5:  resources(resource_id, name, category_id*, unit)
R6:  shelter_inventory(shelter_id*, resource_id*, quantity, reorder_level, last_updated)
```

Surrogate key substitution does not affect normalization — it replaces the determinant but the dependency structure is preserved. The surrogate key `shelter_id` still uniquely determines `name, address, location, capacity, status` with the same structural guarantees.

### 4.2 Case Study 2 — People Hierarchy
**ISA Specialization, 1NF Multivalued, and BCNF**  
*(Covers R7, R8, R9)*

#### Step 0 — Naive Design

A naive single-table approach for all people in the system:

```
naive_persons(
    person_id, name, contact, email, person_type,
    skills_list,        -- comma-separated list, e.g. "first_aid,driving"
    availability,
    assigned_zone,
    medical_conditions, -- comma-separated, e.g. "diabetes,hypertension"
    shelter_id,
    registered_at
)
```

**Sample data showing anomalies:**

| person_id | name | person_type | skills_list | medical_conditions | shelter_id |
|---|---|---|---|---|---|
| 1 | Arjun | volunteer | `"first_aid,driving"` | NULL | NULL |
| 2 | Lakshmi | affected | NULL | `"diabetes,hypertension"` | S2001 |
| 3 | Meera | volunteer | `"cooking"` | NULL | NULL |

**Problems:**
- `skills_list` is a comma-separated string → **violates 1NF**
- `medical_conditions` is a comma-separated string → **violates 1NF**
- Massive NULLs: volunteer fields are NULL for affected persons and vice versa
- Heterogeneous semantics: one table with two very different entity types

---

#### Step 1 — First Normal Form (1NF)

**Violation:** `skills_list` and `medical_conditions` are non-atomic (multi-valued).

**Option A (strict relational):** Create separate tables:
```
volunteer_skills(person_id, skill)       PK: {person_id, skill}
person_conditions(person_id, condition)  PK: {person_id, condition}
```

**Option B (PostgreSQL-specific):** Store as native array types:
- `skills TEXT[]` — supports set operators `@>`, `&&`, `= ANY()`
- `medical_needs JSONB` — flexible schema for variable medical profiles

**The DRRAS adopts Option B** (justified in §5). For the purpose of this normalization analysis, we treat each array/JSONB column as a single atomic column and proceed.

**After 1NF treatment:**

```
persons_1NF(person_id, name, contact, email, person_type,
            skills, availability, assigned_zone,
            medical_needs, shelter_id, registered_at)
```
✅ All values are now treated as atomic.

---

#### Step 2 — Second Normal Form (2NF)

PK is `{person_id}` (single attribute). With a single-attribute PK, **partial dependencies cannot exist** by definition. `persons_1NF` is therefore in 2NF.

---

#### Step 3 — Third Normal Form (3NF) + ISA Analysis

**Violation check:**

No direct transitive dependencies exist in the FD sense. However, the relation has a **semantic anomaly** driven by `person_type`:

- When `person_type = 'volunteer'`: `skills, availability, assigned_zone` are meaningful; `medical_needs, shelter_id, registered_at` are NULL
- When `person_type = 'affected'`: `medical_needs, shelter_id, registered_at` are meaningful; `skills, availability, assigned_zone` are NULL

This is the ER **ISA Specialization** pattern. The problem is not a classic FD violation but a **schema design weakness** — a mixed-type relation with conditional attributes and unnecessary NULLs. The standard normalization technique is **Table-per-Type decomposition**:

**Decomposition into ISA hierarchy:**

```
R7: people(person_id, name, contact, email)
    PK: {person_id}
    Contains common attributes for ALL persons

R8: volunteers(person_id, skills, availability, assigned_zone)
    PK: {person_id}  — also FK → people(person_id)
    Contains ONLY volunteer-specific attributes

R9: affected_persons(person_id, medical_needs, shelter_id, registered_at)
    PK: {person_id}  — also FK → people(person_id)
    Contains ONLY affected-person-specific attributes
```

This decomposition:
- Eliminates all NULLs (a volunteer row has no medical_needs column; an affected person row has no skills column)
- Allows `SELECT * FROM people` to return all persons (via PostgreSQL `INHERITS`)
- Maintains referential integrity via shared PK/FK `person_id`

---

#### Step 4 — BCNF Check

| Relation | FD | Determinant | Superkey? | BCNF? |
|---|---|---|---|---|
| `people` | `person_id → name, contact, email` | `{person_id}` (PK) | ✅ | ✅ |
| `volunteers` | `person_id → skills, availability, assigned_zone` | `{person_id}` (PK) | ✅ | ✅ |
| `affected_persons` | `person_id → medical_needs, shelter_id, registered_at` | `{person_id}` (PK) | ✅ | ✅ |

**All three ISA relations are in BCNF.** The ISA Table-per-Type decomposition naturally produces BCNF-compliant relations.

### 4.3 Case Study 3 — Resource Requests and the Generated Column
**Transitive Dependency via Computed Attribute**  
*(Covers R10)*

#### The Apparent BCNF Violation

```
R10: resource_requests(request_id, zone_id, resource_id,
                       quantity_requested, urgency, priority_score,
                       status, requested_at, fulfilled_at)
```

**FDs identified:**
- F10.1: `request_id → urgency, quantity_requested` (direct)
- F10.2: `(urgency, quantity_requested) → priority_score` (generated formula)
- F10.3: `request_id → priority_score` (via transitivity: F10.1 + F10.2)

The transitive chain `request_id → urgency → priority_score` (combined with `quantity_requested`) creates a dependency where `(urgency, quantity_requested)` is a **non-key determinant** of `priority_score`. In a conventional 3NF/BCNF analysis, this would require decomposition:

```
-- Naive decomposition (if priority_score were a regular stored attribute):
R10a: requests_base(request_id, zone_id, resource_id, quantity_requested,
                    urgency, status, requested_at, fulfilled_at)
R10b: urgency_score_lookup(urgency, quantity_requested, priority_score)
```

However, this decomposition is **unnecessary and incorrect** for the following reason:

#### Why priority_score Does Not Violate BCNF

`priority_score` is declared as a **PostgreSQL GENERATED COLUMN**:

```sql
priority_score INTEGER GENERATED ALWAYS AS (
    CASE urgency
        WHEN 'critical' THEN 40
        WHEN 'high'     THEN 30
        WHEN 'medium'   THEN 20
        WHEN 'low'      THEN 10
    END + quantity_requested
) STORED
```

A generated column is **not an independently stored data attribute** — it is a deterministic function of other columns recomputed by the database engine. It cannot be independently `INSERT`ed or `UPDATE`d. In normalization theory, derived attributes are excluded from FD analysis because:
1. They introduce no data redundancy (the value is always derivable from source attributes)
2. They cause no update anomalies (updating `urgency` automatically recomputes `priority_score`)
3. They cannot create insert/delete anomalies (the value is always consistent)

**Formal argument:** Removing `priority_score` from the FD analysis, R10 becomes:

```
R10_base(request_id, zone_id, resource_id, quantity_requested, urgency,
         status, requested_at, fulfilled_at)
FDs: request_id → {all attributes}
CK: {request_id}
```

Every non-trivial FD has `{request_id}` (a superkey) as its determinant. **R10 is in BCNF.**

The presence of `priority_score` as a generated column is a **performance optimization** (avoids recomputing scores on every query) that does not compromise normalization correctness.

## 5. Acknowledged 1NF Design Exceptions

Three attributes in the schema store non-atomic values. Each is a deliberate design decision with explicit justification:

### 5.1 `volunteers.skills` — PostgreSQL TEXT[]

**Strict 1NF requires:** A separate `volunteer_skills(person_id, skill)` table with PK `{person_id, skill}`.

**Design choice:** `TEXT[]` (PostgreSQL native array type).

**Justification:**
1. **Query efficiency:** Array operators (`@>`, `&&`, `= ANY()`) run as index scans on GIN indexes — more efficient than a JOIN to a separate table for skill-matching queries
2. **No independent identity:** Individual skills have no attributes of their own; they are simple string tags. A separate table would provide no analytical benefit
3. **Operational simplicity:** Skill sets are always read/written together; splitting them would require transactions for every volunteer profile update

**MVD analysis:** The technically correct 4NF treatment would split into `volunteer_skills(person_id, skill)` to eliminate the MVD `person_id →→ skill`. The schema acknowledges this trade-off in favour of PostgreSQL-specific efficiency. In a MySQL/Oracle environment (which lack native array types), the 4NF decomposition would be mandatory.

### 5.2 `affected_persons.medical_needs` — PostgreSQL JSONB

**Strict 1NF requires:** A `person_conditions(person_id, condition_type, condition_value)` EAV-style table.

**Design choice:** JSONB document.

**Justification:**
1. **Schema volatility:** Medical profiles are unpredictable — a person may have `{"wheelchair": true, "oxygen_required": false, "conditions": ["diabetes"], "medications": ["Metformin"], "blood_type": "O+"}`. No fixed set of columns can represent this without either sparse columns or an EAV anti-pattern
2. **JSONB query support:** `WHERE medical_needs @> '{"wheelchair": true}'` performs an indexed GIN scan — equivalent expressive power to a normalized table, with far less JOIN complexity
3. **Audit integrity:** The full medical profile travels as a single unit in `audit_log.old_values`/`new_values`, preserving atomic medical snapshots

### 5.3 `donation_records.items` — PostgreSQL JSONB Array

**Strict 1NF requires:** A `donation_items(donation_id, resource_id, quantity)` table.

**Design choice:** JSONB array `[{"resource_id": 5, "quantity": 100}, ...]`

**Justification:**
1. **Immutable audit record:** `donation_records` is an immutable receipt. The items list is processed once (unpacked into `shelter_inventory` via UPSERT) and then archived. A normalized `donation_items` table would add JOIN complexity with no query benefit
2. **Variable composition:** A single donation event may contain 1 to 50 different resource types. JSONB array handles this without pre-defining row count
3. **Processing pattern:** The UPSERT logic iterates the array application-side; the database does not need to query `items` relationally

## 7. Summary

The DRRAS database schema achieves BCNF normalization through the following design decisions:

| Normalization Technique | Where Applied |
|---|---|
| **Surrogate PKs** replace natural keys | All 14 relations — eliminates update anomalies from name changes |
| **Composite PK** for M:N junction | R6 `shelter_inventory` — eliminates partial dependencies from the naive flat stock table |
| **ISA Table-per-Type decomposition** | R7–R9 (`people`, `volunteers`, `affected_persons`) — eliminates NULL-heavy mixed-type rows |
| **Self-referencing FK** (not a separate relation) | R4 `resource_categories` — BCNF-safe because `parent_id` is not a determinant |
| **Generated column** for derived FD | R10 `resource_requests.priority_score` — computed formula; excluded from FD analysis |
| **Acknowledged 1NF exceptions** | R8 (`skills`), R9 (`medical_needs`), R13 (`items`) — PostgreSQL-specific optimizations justified by query patterns and schema volatility |
| **Two candidate keys** | R12 `volunteer_shifts` — both `{shift_id}` and `{volunteer_id, duty_period}` are CKs; every FD determinant is a CK → BCNF holds |
